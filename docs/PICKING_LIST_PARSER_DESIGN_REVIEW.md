## 2. 문서 구조 요약 — 검토

- **타이틀/ID:** PICKING LIST, Customer reference, Requisition, Sales order 등 → **페이지 1에서만 확정**하는 전제는 타당. 다만 **여러 페이지에 헤더가 반복**될 수 있으므로 “첫 번째 유효 블록만 사용” 규칙을 명시할 것.
- **품목(본품/샘플):** 자재코드(8자) + 설명 + 총량 + 단위 + Batch 라인 반복 → **라벨-라인 기반**이 표 파싱보다 안정적이라는 결론 동의.
- **Packing/Weight:** Net·Gross·Big bag·pallet 등 별도 블록 → **키워드(Net, Gross, Big bag, ea 등) 기반** 추출 권장.

**권장 보완:**  
- “Item 시작”을 **자재코드 정규식만**으로 잡으면, 다른 8자리 숫자(예: Sales order 80007418)가 같은 페이지에 있을 때 오탐 가능. **라인 컨텍스트**(이전 라인이 빈 줄 또는 "Item" 등) 또는 **고정 컬럼 위치**를 보조 조건으로 두는 것이 안전.

## 3. “절대 실패하지 않는” 파싱 아키텍처 — 검토

### 3.1 정의 (프로그램 불크래시, 빈 값·오류 명시, 하드스톱)

- **예외로 죽지 않음:** try/except로 파서 전체를 감싼 뒤, 실패 시 `PickingDoc(errors=[...])` 반환 권장. 초안도 이 방향.
- **값 없음 → (비어있음 + errors[] + 디버그 증거):** `doc.errors`에 “어떤 블록을 찾지 못했는지” 넣는 것은 좋음. **증거**로 “해당 라인 일부(raw)”를 errors에 포함하면 운영 시 원인 추적에 유리.
- **이상 데이터 하드스톱:** 검증 실패 시 **출고 실행을 차단**하고, 파싱 결과는 “성공 + errors”가 아니라 **success=False + errors**로 두어, 상위에서 “파싱은 됐지만 검증 실패”로 분기하는 것을 권장.

### 3.2 파이프라인

- **PDF 타입 판별 → Text vs OCR:**  
  - 텍스트 추출 글자 수가 임계치(예: 100자) 미만이면 OCR 분기하는 방식 적절.  
  - OCR 경로에서도 **동일한 상태머신**에 텍스트만 넣는 구조는 유지보수에 유리.
- **Header / Item / Packing 파서 분리:**  
  - 단일 패스에서 “현재 블록” 상태를 두고 라인별로 전이하는 **상태머신**이면, 페이지가 여러 장이어도 동일 규칙 적용 가능.  
  - **페이지 경계:** “새 페이지에서 헤더가 반복되면 무시” 규칙을 명시할 것.

## 4. 정규식·상태머신 — 상세 검토

### 4.1 ITEM_LINE_RE

```text
^(?P<mat>\d{8})\s+(?P<desc>.+?)\s+(?P<qty>[\d,]+\.\d+)\s+(?P<unit>[A-Z]{2})\s+(?P<status>\w+)\s*$
```

- **문제 1:** `.+)`는 탐욕적이어서, 설명(desc) 안에 숫자(예: "300.00 MT")가 있으면 qty와 겹칠 수 있음. **비탐욕 `.+?`**는 “가능한 한 짧게”이므로, qty가 “마지막 등장 숫자”를 잡도록 **qty를 라인 끝 쪽에서 찾는** 구조가 더 안전 (예: `\s+([\d,]+\.\d+)\s+(MT|KG)\s+(\w+)\s*$` 로 끝 3개 그룹 고정).
- **문제 2:** 실제 PDF는 **공백이 여러 칸**이거나 **탭**일 수 있음. `\s+`로 연결하는 것은 괜찮으나, **숫자 그룹**에서 `[\d,]+\.\d+`는 정수만 있는 경우(예: `60`)를 놓침. `[\d,]+\.?\d*` 또는 `[\d,]+(?:\.[\d]+)?` 형태 권장.
- **문제 3:** `status`가 `\w+`이면 "Cleared" 등 한 단어만 가정. 실제로는 "Customs status" 등이 다를 수 있으므로, **선택적**으로 두거나, “MT/KG 뒤 나머지”를 한 덩어리로 두는 편이 안전.

### 4.2 BATCH_LINE_RE

```text
^Quantity:\s*(?P<qty>[\d,]+\.\d+|\d+)\s*(?P<unit>[A-Z]{2})\s+Batch number:\s*(?P<batch>\d+)\s+Storage location:\s*(?P<sloc>\d+)\s+(.+)$
```

- **문제 1:** `Batch number:` 뒤가 **문자열(LOT 번호)**일 수 있음. 현재 `\d+`면 10자리 LOT는 되지만, 앞자리 0이 사라질 수 있음. **문자열로 보존**하려면 `(?P<batch>\S+)` 또는 `(.+?)` 후 trim.
- **문제 2:** “Storage location”이 "1001 GY logistics"처럼 **여러 토큰**일 수 있음. `\d+`만 쓰면 "1001"만 잡고, "GY"는 다음 필드로 넘어갈 수 있음. 실제 PDF 레이아웃에 맞춰 캡처 범위 조정 필요.
- **문제 3:** Batch 라인이 **여러 줄**로 나뉘어 있는 PDF(예: Quantity: 다음 줄에 5.00 MT)면 한 라인 정규식으로 실패. **멀티라인** 또는 “Quantity:” 감지 후 다음 1~2줄을 합쳐서 파싱하는 로직이 필요할 수 있음.

### 4.3 Header 수집 로직

- `doc.customer_ref is None`일 때만 설정 → **첫 번째 매칭만** 사용. 좋음.
- `requisition_no`를 “4~5자리 숫자”로만 잡으면, 3073 같은 값은 잡지만 **다른 4자리 숫자**(날짜 일부 등)와 혼동 가능. **키워드 접두어**("Requisition", "Sales order" 등)가 있는 라인에서만 추출하도록 권장.
- **Creation Date:** `\d{2}\.\d{2}\.\d{4}`만으로는 "29.01.2026" 등 구분자 변형(.-/) 대비가 필요. `datetime.strptime`으로 파싱 시도 후 실패하면 해당 라인을 스킵하는 방식이 안전.

## 5. 데이터 모델 — 검토

- **PickingDoc / ItemBlock / BatchLine:** 역할이 분리되어 있어 적절.
- **SQM 연동 관점 보완:**
  - **BatchLine.batch_no** → SQM **lot_no**와 매핑. Allocation은 "LOT 1행 = 1배치"이고, Picking List의 Batch number가 LOT 번호와 동일하다는 전제가 필요. 문서에 "Batch number: 1125052654" 형태로 나오면 **lot_no**로 사용 가능.
  - **outbound_date / plan_loading_date:** Picking List의 "Plan Loading Date"를 출고일로 넣을지, Sales Order의 "Delivery Date"를 넣을지 정책 명시 필요. 설계서대로라면 **Picking List = 실행 트리거**이므로 Plan Loading Date를 **outbound_date**로 두는 것이 맞음.
  - **sales_order / requisition_no:** DB의 `outbound` 또는 `allocation_plan`에 **sale_ref** 외에 **picking_requisition**, **sales_order_no** 컬럼이 있으면 추적에 유리.

| 4 | 본품 배치 집합 == 샘플 배치 집합 | ✅ | 1:1 정책 유지 시 적절. 다만 “샘플이 본품보다 적은” 문서가 오면 경고 후 진행할지 정책 필요 |
| 5 | 300,000 kg = 600 bag | ✅ | Packing 블록에서 "Big bag 500kg" 수량을 파싱해 **동적으로** 검증하는 편이 확장성 좋음 |
| 6 | 15 x40' → 컨테이너당 목표 중량 근접 | ✅ | ±허용 오차(예: ±5%) 명시 권장 |
| 7 | 단위 MT→kg 내부 표준 | ✅ | 유지 |

## 7. 피킹 플랜 생성 로직 — 검토

- **본품 5 MT/배치 → 5,000 kg → 500 kg 톤백 10개:** SQM 톤백 무게가 500 kg 전제와 일치. **DB 톤백 무게가 500이 아닌 LOT**는 별도 정책(경고 또는 무게 기반 재계산) 필요.
- **샘플 1 kg/배치:** 배치당 1개. **is_sample=1** 톤백과 매핑 시, Picking List의 “1.00 KG”가 샘플 1톤백(1 kg)으로 매핑되면 됨.
- **컨테이너당 4배치:** 60배치 ÷ 15 = 4배치/컨테이너. **결정론적 round-robin**이면 항상 같은 결과. 다만 **배치 순서**가 PDF 순서와 SQM **LIFO(큰 sub_lt 먼저)** 순서와 일치하는지는, Picking List의 Batch 순서와 DB 톤백 순서를 **같은 정렬**로 맞출지 정책 필요.

---

## 8. SQM 3단계(Allocation → Picking → Sales Order)와의 정합성

- **Allocation:** 예정표, 톤백 RESERVED. **날짜 없음.**
- **Picking List:** 실행 지시, **Plan Loading Date**로 출고일 확정, RESERVED → PICKED.
- **Sales Order:** 확정, PICKED → SOLD.

파서 출력에 **plan_loading_date**를 반드시 넣고, 출고 실행 시 이 날짜를 **outbound_date**로 사용하면 3단계와 일치.  
또한 **Requisition / Sales order 번호**를 저장해 두면, 나중에 Sales Order 파일과 “같은 출고 건”으로 매칭할 때 유리.

---

## 9. 구현 시 권장 사항(요약)

1. **실제 PDF 샘플**로 정규식·상태머신을 단위 테스트하고, **여러 페이지·여러 고객** 샘플로 회귀 테스트.
2. **OCR 경로**는 동일 상태머신 + 전처리(이미지 보정, 레이아웃 분석)만 추가.
3. **에러 메시지**에 “실패한 라인(raw)” 일부를 포함해, 현장/운영에서 원인 파악이 쉽게 할 것.
4. **자재코드(30000008, 30000026)**를 상수로 두지 말고, **설정 또는 문서 첫 블록에서 추출**해 검증에 쓰면 다른 고객/제품에도 재사용 가능.
5. **Picking List 파서 결과 → SQM 엔진**은 “배치(LOT) 단위 톤백 수 + 출고일”을 넘기고, **reserve_from_allocation**과 유사하게 “이미 RESERVED인 LOT에 대해 Picking List 기준으로 PICKED 전환”하는 API를 두는 것이 설계서와 맞음.

## 10. 결론

- **전체 방향(라벨-라인 파싱, Text/OCR 분기, 하드스톱 검증, 배치 단위 피킹 플랜)**은 타당하고, “절대 실패하지 않게” 가기 위한 토대가 잘 잡혀 있음.
- **정규식·캡처 그룹·멀티라인·헤더 추출**은 실제 PDF 레이아웃으로 검증·보완 필요.
- **SQM와의 연동**은 Allocation(예정) → Picking(실행, outbound_date 반영) → Sales Order(확정) 3단계와 RESERVED→PICKED→SOLD를 명시해 두고, Picking List 파서 결과를 “출고 실행” 입력으로 넣는 흐름을 한 번 더 설계서에 반영하는 것을 권장.

이 검토안을 기준으로 파서·피킹 플랜 구현을 진행하면, 실패 방지와 운영 추적성 모두 확보하기 수월합니다.
