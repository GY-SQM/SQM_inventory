# SQM 메뉴 7개 개편안 — 의견 및 적용 시 유의점

**기준일:** 2026-02-21  
**현재 구조:** 7개 탑레벨 (📁 파일 · 📝 보고서 · 🔧 도구 · 🚀 v2.7 · 👁️ 보기 · ❓ 도움말 · 📦 품목)  
**개편안:** 7개 탑레벨 (📁 파일 · 📥 입고 · 📤 출고 · 📦 재고 · 📊 보고서 · ⚙️ 설정/도구 · ❓ 도움말)

---

## 1. 의견: 개편 적용해도 됨

- **업무 흐름에 맞음:** 입고 → 재고 관리 → 출고 → 보고서 순서가 메뉴 순서와 같아져서 직관적입니다.
- **파일 메뉴 정리:** 지금은 “파일” 안에 입고·출고·내보내기·백업·도구가 모두 있어서 무겁고, 개편 후에는 “파일”은 내보내기·백업·최근파일·종료만 담당하게 됩니다.
- **기능/엔진 코드와 무관:** 메뉴에서 호출하는 콜백(`_on_pdf_inbound`, `_on_outbound_click` 등)은 그대로 두고, **어디에 붙이느냐**만 바꾸는 수준이라 데이터나 로직 쪽 리스크는 거의 없습니다.
- **단축키 유지:** Ctrl+I, Ctrl+O, Ctrl+E, Ctrl+B, F5 등은 `_setup_keyboard_shortcuts()`에서 그대로 바인딩되므로 메뉴를 7개로 바꿔도 동작은 동일합니다.

---

## 2. 지금 적용 시 “혼란” 가능성

| 구분 | 내용 |
|------|------|
| **사용자 습관** | “파일 → 입고 → PDF 입고”에 익숙한 분은 며칠간 “입고 → PDF 입고”로 바뀐 걸 찾으실 수 있음. 경로가 짧아져서 대부분 금방 적응 가능한 수준. |
| **실제 위험** | 메뉴 위치만 옮기는 것이므로, 기능 누락·데이터 오류 같은 **구조적 혼란**은 없음. |

정리하면, **“혼란”은 짧은 적응 기간 수준**이고, 적용 자체를 막을 만한 위험은 없습니다.

## 3. ⚠️ 반드시 유의할 점 (v6.0.2 기준)

현재 저장소에는 **menu_registry.py**로 입고/출고 항목을 한 곳에서 관리하고 있고,  
**Picking List 업로드 (PDF)** 등이 그 레지스트리를 통해 “파일 → 출고” 안에 들어가 있습니다.

- **업로드하신 7개 개편안**은 이 레지스트리를 쓰지 않고, 입고/출고를 **custom_menubar에 직접 나열**하는 방식입니다.
- 그대로 적용하면:
  - **menu_registry를 쓰지 않게 되어**, 커스텀 메뉴와 네이티브(fallback) 메뉴가 다시 어긋날 수 있고,
  - **출고** 메뉴에 “Picking List 업로드 (PDF)”, “Allocation 입력 (파일/붙여넣기)”가 **없을 수 있습니다.**  
    (개편안에는 “Allocation 출고 예약” 등은 있지만, v6.0.2에서 쓰는 `_on_allocation_input_unified`, `_on_picking_list_upload`와 라벨/구성이 다를 수 있음.)

그래서 **지금 적용할 때는 다음을 권장합니다.**

1. **7개 구조는 그대로 도입** (파일 / 입고 / 출고 / 재고 / 보고서 / 설정·도구 / 도움말).
2. **입고·출고 항목은 menu_registry 계속 사용**  
   - “입고” 탑레벨 메뉴 → `FILE_MENU_INBOUND_ITEMS`로 구성  
   - “출고” 탑레벨 메뉴 → `FILE_MENU_OUTBOUND_ITEMS`로 구성  
   → Picking List, Allocation 입력, 바코드 스캔, Sales Order 등이 **한 번만 정의**되고, 커스텀/네이티브 둘 다 동일하게 표시되게 유지.
3. **개편안에만 있는 항목** (로케이션 업로드, 간편 출고, 배정표 출고, Excel 출고, 배치 출고, 테마, 품목관리 등)은  
   - 기존 개편안 코드를 참고해 **같은 7개 구조 안에** 추가하되,  
   - 가능하면 나중에 레지스트리로 끌어와서 “한 곳에서 정의”하도록 정리.

## 5. 결론

- **개편안 자체:** 적용해도 되고, 화면도 더 깔끔해지며 업무 흐름과 맞습니다.
- **지금 적용해도 되는지:** 네. 다만 **그대로 덮어쓰기보다는**,  
  - 7개 탑레벨 구조를 따르고,  
  - **입고/출고는 menu_registry를 계속 쓰도록** 맞추어 적용하면,  
  Picking List 누락·커스텀/네이티브 불일치 같은 혼란을 피할 수 있습니다.

원하시면 이 방향으로 `custom_menubar.py` / `menu_mixin.py` 수정 초안(패치 형태)도 정리해 드리겠습니다.
